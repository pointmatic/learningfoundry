# Templated Recipes — Feature Spec (upstream candidate for LearningFoundry)

**Status:** project-local implementation shipped (Story E.d, `scripts/render_recipe.py`);
the LearningFoundry capability described here is **specced for future upstreaming, not
built** (developer-deferred). This doc is the contract the project-local script realizes
today and the migration target for when LF (or ModelFoundry) absorbs it.

> **The formal LF feature request lives in
> [`recipe-template-features.md`](recipe-template-features.md)** —
> the buildable spec (declared-in-exercise-YAML authoring, the typed-placeholder
> "recipe doubles as parameter schema" design, DR/MF tool-agnostic output, YAML-now /
> JSON-later). This doc remains the project-side convention + migration notes.

---

## §1 Problem — a recipe is a technical artifact, not a learner surface

A ModelFoundry/DataRefinery recipe is a precise, interdependent YAML document: plugin,
architecture, loss, optimizer, training, evaluation, output expectations. An exercise's
**pedagogical pinhole** (see `curriculum-exercise-authoring-golden-path.md`) names the
*few* things the learner manipulates — for the CNN, that is a handful of
hyperparameters (learning rate, weight decay, batch size, epochs) and, for the tuning
view, the Optuna budget + search ranges. The rest of the recipe is backdrop.

Handing a learner the raw recipe to edit is the wrong altitude — the analogy is editing a
`.docx` by hand-tweaking its XML instead of using the app's controls. We want the learner
to change **only the surfaced parameters**, as plain Python variables, and have a concrete,
valid recipe rendered behind the scenes.

---

## §2 Project-local mechanism (shipped, E.d) — strict deep-merge override

`scripts/render_recipe.py` renders a concrete recipe from a `*.template.yaml` **base** +
a `params` override mapping.

- **The template is a complete, valid recipe** with every knob at its default value, so
  `modelfoundry validate <template>` passes as-is. No `${...}` placeholder tokens (which
  would break YAML parsing and MF validation) — see §3 for why this beats substitution.
- **`params` is a partial mapping** mirroring the recipe's nesting. `apply_overrides`
  recursively overlays it onto the template and returns a new dict (template untouched).
- **The merge is strict.** An override key absent from the template, or a leaf that changes
  between scalar and mapping, raises `RenderError`. This *is* the param-surfacing contract:
  you may override only knobs the template already declares, so a typo (`lr` for
  `learning_rate`) fails loud rather than silently injecting an unknown key MF later rejects.
- **Key order follows the template**, so the rendered YAML preserves the template's layout.
- The rendered file carries a `# GENERATED by scripts/render_recipe.py …` provenance header.

CLI (also importable: `render_recipe(template_path, params, out_path=...)`):

```bash
# defaults
python scripts/render_recipe.py models/resnet20.template.yaml --out rendered.yaml
# override surfaced knobs (each VALUE parsed as a YAML scalar)
python scripts/render_recipe.py models/resnet20.template.yaml \
    --set Optimizer.learning_rate=0.002 --set Training.batch_size=96 --out rendered.yaml
# override from a nested params file (required for dotted search_space keys — see §5)
python scripts/render_recipe.py models/resnet20_optuna.template.yaml --params p.yaml --out rendered.yaml
```

## §3 Why deep-merge override, not placeholder substitution

| | Strict deep-merge (chosen) | Placeholder substitution (`${lr}` / Jinja) |
|---|---|---|
| Template validity | Template is a real recipe; `modelfoundry validate` passes as-is | Template has holes; can't validate until rendered |
| Dependency weight | stdlib + PyYAML (already present) | adds a templating engine (Jinja) or bespoke tokenizer |
| Typo safety | Override-unknown-key → `RenderError` | Unfilled/misspelled token → silent string or render-time error |
| Typing | Override value keeps its YAML type | String interpolation needs explicit re-typing |
| Surfaced-knob contract | "Override only what the template declares" is enforced structurally | Surface is whatever tokens happen to exist |

The decisive property: the template **is** the default recipe, so the "render with no
params" path produces (modulo comments) the canonical recipe, and the smoke test is simply
"render defaults → validate."

## §4 Project templates + surfaced parameters

| Template | Mirrors | Surfaced knobs (override paths) |
|---|---|---|
| `models/resnet20.template.yaml` | `models/resnet20.yaml` (Req B/C/D) | `Optimizer.learning_rate`, `Optimizer.weight_decay`, `Training.batch_size`, `Training.max_epochs` |
| `models/resnet20_optuna.template.yaml` | `models/resnet20_optuna.yaml` (Req E) | `Optimization.n_trials`, `Optimization.max_epochs_per_trial`, the four `Optimization.search_space.*` ranges |

Each template's header block documents the surfaced knobs and their defaults inline.

## §5 Known limitations (carry into the LF feature design)

1. **Coupled parameters.** `resnet20.template.yaml`'s `Optimizer.schedule.T_max` (cosine
   period) is conventionally `== Training.max_epochs`. The merge treats them independently,
   so a learner who changes `max_epochs` substantially must also override `T_max`. A real LF
   feature should let a surfaced knob drive **multiple** recipe paths (one `epochs` → both).
2. **Literal dotted keys.** `Optimization.search_space` keys are literal dotted strings
   (`"Optimizer.learning_rate"`). `apply_overrides` matches them verbatim (correct), but the
   CLI `--set` flag splits on dots and **cannot** target them — use a `--params` file for
   search ranges. An LF feature with a declared param schema avoids this ambiguity.
3. **No range/type validation beyond shape.** The merge enforces "key exists" and
   "scalar↔mapping shape," not "LR ∈ (0, 1)." Surfaced-knob *ranges* are a schema concern the
   LF feature should own (and could expose to the UI as sliders/inputs).
4. **Template ↔ live-recipe drift.** Until the feature lands, each `*.template.yaml` mirrors
   a live recipe (`resnet20.yaml`, `resnet20_optuna.yaml`) and must be kept in sync by hand.
   The LF feature collapses this to one source (the templated recipe **is** the recipe).

## §6 Migration path to a LearningFoundry capability

When LF (or MF) absorbs this, the project-local script retires. The target shape:

- A recipe declares a **`parameters:` schema** — surfaced knob → {path(s), type, range/choices,
  default, label} — so the surface is explicit, multi-path coupling is expressible (§5.1), and
  ranges are validated and UI-renderable (§5.3).
- The exercise/runtime renders the concrete recipe from that schema + the learner's values; no
  separate template file and no hand-kept mirror (§5.4).
- `scripts/render_recipe.py` + the two `*.template.yaml` files are deleted; the exercise binds
  surfaced variables directly to the declared schema.

Until then: **project-local script now, LF feature later** (developer-deferred).
